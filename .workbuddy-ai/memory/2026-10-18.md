# 2026-10-18

## Full-screen ads disabled

`AdConfig.FULL_SCREEN_ADS_ENABLED = false` is the single switch. Guards were added to
`AppOpenAdManager.loadAd` / `showAdIfAvailable` (ExtremisBrowserApplication) and to
`loadInterstitialAd` / `showInterstitialIfReady` (MainActivity). The load/show calls are still
present and simply return early, so flipping the flag restores the old behaviour. Banner and
native ads are untouched.

## Swipe-to-refresh reloaded the page on every upward scroll

`SwipeRefreshLayout` asks its direct child `canScrollVertically(-1)` to decide whether a pull is
allowed. The child is `webHost`, a plain `FrameLayout`, which can never scroll — so *every*
downward drag anywhere on the page was treated as a refresh. Fixed with
`setOnChildScrollUpCallback { _, _ -> activeWebView?.canScrollVertically(-1) }` plus a longer
`setDistanceToTriggerSync` (88dp).

## Downloads screen only knew about DownloadManager

`DownloadsActivity` queried `DownloadManager` alone, so anything the video downloader published
through MediaStore (`Download/ExtremisBrowser/`) was invisible. It now merges two sources:
`queryDownloadManager()` and `queryPublishedDownloads()` (MediaStore on API 29+, direct folder
listing below). Published rows get **negative ids** so delete/open route to `ContentResolver`
instead of `DownloadManager.remove`.

## Why YouTube downloads produced 31-byte files

The two broken files on the device contained the protobuf string `sabr.malformed_config`. Modern
YouTube playback goes through the SABR endpoint, which needs a POST with a protobuf body; a plain
GET of the same URL answers with that 31-byte error. `MediaDetector` now rejects
`videoplayback` URLs carrying `sabr=1`, leaving only the player-response format URLs
(`YouTubeExtractor`), which are genuinely GET-able. Earlier successful Shorts downloads
(2.8–5.5 MB, real titles) confirm that path works when the SABR junk is excluded.

## "Can't view" a download

`resolveMimeType` guessed the type from the URI extension, but both DownloadManager and MediaStore
return `content://` URIs with **no extension**, so it always fell through to `*/*` and no player
accepted the intent. `DownloadItem` now carries a `mimeType` taken from
`DownloadManager.COLUMN_MEDIA_TYPE` / `MediaStore.MEDIA_TYPE`.

## YouTube format collection

The sniffer only tried `window.__extremisCollectFormats()` once at 2.5 s. Shorts swaps videos
without reloading the document, so it now retries at 1.5/3.5/6.5/11 s and again on
`yt-navigate-finish`. `showMediaSheet()` additionally asks the page to collect on demand when the
URL is a YouTube watch/Shorts URL, then opens the sheet 450 ms later.

## Gotcha worth remembering

Writing `*/*` inside a KDoc `/** ... */` block **closes the comment early** (the `*/` inside), and
the rest of the sentence is parsed as code. Broke the build in `DownloadItem.kt`. Use "the wildcard
type" in prose instead.

## YouTube: not downloadable with this architecture

Measured, not guessed:

- `window.ytInitialPlayerResponse` exists but holds **only** `playabilityStatus` (no
  `streamingData`). The real response comes from a POST to `/youtubei/v1/player`, whose body a
  WebView cannot replay.
- Every network `videoplayback` request carries `sabr=1`. A plain GET answers
  `sabr.malformed_config` (31 bytes) — the broken files.
- Hooking `fetch` + `XMLHttpRequest` in the page **does** capture the player API response
  (confirmed: `playerApi fetch=1`), but the single format it returns is `signatureCipher`-only.
  `YouTubeExtractor` drops ciphered entries, so `parsed=0`.
- Deciphering needs YouTube's obfuscated player JS. Not implemented — it changes constantly and a
  half-working implementation would silently produce broken files. VidMate resolves server-side.

Conclusion: YouTube needs a server-side resolver. The `fetch`/XHR hook is still worth keeping —
it works the moment YouTube hands back a plain `url`.

## Fragment bug — why downloads would not play at all

`Facebook.mp4` began with `moof`/`mfhd`/`traf`/`tfdt`/`trun` and had **no `ftyp`/`moov`**: it was
one fragment of a fragmented MP4. The sniffer was saving whatever byte window the player asked for.
Fixed by running `stripRangeParams` over **every** detected URL (not just YouTube) and adding
Facebook's `bytestart` / `byteend` to the stripped parameter list. Not yet re-tested against a real
Facebook video.


## Capture hook: why it only worked after an in-site navigation

The capture hook replaced `MediaSource.prototype.addSourceBuffer` from `onPageFinished`. That is
always too late when a page is opened **directly** on a video (bookmark, external intent, shared
link): YouTube buffers the clip while the document is still loading, so the hook missed every
`appendBuffer`. It only worked earlier because the sniffer had been injected on the YouTube home
page first, and YouTube is an SPA — no document reload meant the hook survived into the player page.

Fixed with `WebViewCompat.addDocumentStartJavaScript` (`androidx.webkit:webkit:1.11.0`), which runs
before page script. `installDocumentStartCapture()` is called in `createConfiguredWebView` right
after `addJavascriptInterface`. `onPageFinished` still injects the same asset as a fallback for
WebView builds without the API; `__extremisCaptureInstalled` makes it idempotent.

The hook is now a standalone asset (`media_capture.js`) and patches `SourceBuffer.prototype.appendBuffer`
rather than each instance, so a SourceBuffer created before the hook still gets captured. Kind is
taken from the mime when we saw `addSourceBuffer`, otherwise sniffed from the init segment's codec
fourcc / WebM `V_`/`A_` ids.

## Two bugs that made the saved file unusable

1. `onPageFinished` called `MediaCapture.clear()` on URL change — and the player buffers *before*
   the page finishes, so it deleted the init segment that had just arrived. Moved the clear to
   `onPageStarted` (a new document really starts there), guarded by `isActiveSession` so a
   background tab cannot wipe the visible tab's capture.
2. `saveToDownloads` closed the streams but left the `sizes` map, so the next `appendBuffer`
   re-opened `video.bin` with **truncate** while the muxer was reading it. A 3.8 MB capture
   produced a 153 KB file. Fixed by `detachLocked()`: rename to `<track>.snapshot` and drop the
   bookkeeping under the lock, so playback continues into a fresh file. `clear()` also removes
   stale snapshots.

Verified end to end on `watch?v=dQw4w9WgXcQ`: 1.47 MB video + 0.98 MB audio captured, muxed to
`video_20261018_123903.webm` = 5,042,715 bytes, VP9 + Opus, 61 clusters, played in the Samsung
player. Shorts swipe reset verified by sampling the file during the swipe: 381,656 → 79,398 → 462,870,
i.e. the previous Short's bytes were discarded and a new capture started.

## Ads re-enabled + $5 ad-free subscription

User asked to put every ad format back with sensible UX, add a $5/month ad-free subscription,
then produce the signed release.

Placement (four formats, four different surfaces, never two on one screen):
- **Banner** — bottom of the main browser view plus Bookmarks, Downloads, History, Settings.
- **Native** — inside the New Tab Page feed, between the shortcut tiles and "Recently visited".
- **Interstitial** — `maybeShowInterstitial(url)` at the end of `onPageFinished`. Skips the first
  `INTERSTITIAL_WARMUP_PAGES` (3) pages, then every `INTERSTITIAL_PAGE_INTERVAL` (3rd) page, with a
  `INTERSTITIAL_COOLDOWN_MS` (90 s) floor. Also skipped in incognito, on non-http URLs, when the
  WebView is not on screen, in fullscreen video, and whenever `MediaCapture.hasVideo()` is true.
- **App-open** — on launch via `ExtremisBrowserApplication`, 4 h expiry.

`AdConfig.FULL_SCREEN_ADS_ENABLED` is back to `true`. Rewarded units (`…/6949620879`,
`…/5440088923`) are deliberately **not** wired: AdMob requires rewarded ads to grant a reward and a
browser has no natural one. User confirmed "skip rewarded ads".

Billing: `billing/BillingManager.kt` (Play Billing 7.0.0), product id `ad_free_monthly`.
Entitlement is cached in `BrowserPreferences.adFree` (`AD_FREE_KEY`) so ads stay off on the first
frame and offline; `refresh()` only clears it on a **successful** empty purchase query, never on a
network error. Price is read from Play (`pricingPhaseList.lastOrNull()` — the last phase is the
recurring one, earlier ones are intro/trial), with a `$5.00` fallback before Play answers.

Ad-free gates live in three places and all must stay in sync: `MainActivity.refreshAdVisibility`
(`!incognito && !adFree` hides banner + native + interstitial), `showInterstitialIfReady`,
`maybeShowInterstitial`, and `ExtremisBrowserApplication.loadAd` / `showAdIfAvailable`.

Gotchas found while verifying:
- `ad_free_price_fallback` must be a bare price (`$5.00`); `remove_ads` and `ad_free_message` append
  `/month` and `per month` themselves. The first version produced "$5.00/month per month".
- The subscription product does **not** exist in Play Console yet, so `queryProductDetailsAsync`
  returns nothing and the Subscribe button correctly shows "Subscriptions are not available right
  now". The product must be created in Play Console before the flow can complete.
- On this device Play answers an empty purchase list, so a hand-written `AD_FREE_KEY=true` is
  cleared again on the next `refresh()`. Airplane mode does not help — Play answers from its
  on-device cache. The ad-free render path was instead verified through **incognito**, which uses
  the identical `shouldShowAds == false` branch.
